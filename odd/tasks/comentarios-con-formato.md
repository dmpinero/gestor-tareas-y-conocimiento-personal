# comentarios-con-formato

Objective: comments (task, subtask, workflow step) are written in a rich-text editor and stored as sanitized HTML.
Branch: `feat/comentarios-con-formato` (worktree `../gestor-tareas-y-conocimiento-personal-worktrees/comentarios-formato`). Delivery: stacked-to-main (cached choice), child merged into parent before main.
Runners: backend `uv run pytest` (+ ruff, mypy, lint-imports); frontend `pnpm vitest run`, `vue-tsc --build`, oxlint, eslint, prettier; e2e Playwright on an isolated stack.

## Specs

- **S1 — Editor.** "Quiero que los comentarios aparezcan en un componente que permita cambiar el color, poner negritas, etc." Formats approved by the user ("ok"): **negrita, cursiva, subrayado, tachado, color de texto, resaltado, listas (con viñetas y numeradas) y enlaces**. Applies to the three places that use `ComentariosTarea.vue`: task comments (DetalleTarea), subtask comments (SubtareasTarea), workflow step comments (VistaWorkflows). Both the new-comment input and the edit input use the editor. Toolbar buttons are icon buttons with Spanish accessible names and `aria-pressed`: "Negrita", "Cursiva", "Subrayado", "Tachado", "Color del texto", "Resaltado", "Lista con viñetas", "Lista numerada", "Enlace". Color and highlight pick from a fixed palette plus a "quitar" option; the link asks for a URL (http/https/mailto) inline (no `window.prompt`). Keyboard shortcuts of Tiptap keep working; Ctrl/Cmd+Enter still submits. The editable area keeps the old accessible names ("Escribe un comentario", "Nuevo texto del comentario …") with `role="textbox"` and `aria-multiline="true"`.
- **S2 — Display.** Comments render their formatting (not literal tags) in all three places, through a frontend sanitizer (DOMPurify, same allowlist as S3) as defense in depth.
- **S3 — Backend sanitizing (security).** The API stores and returns sanitized HTML. Allowlist: tags `p, br, strong, em, u, s, ul, ol, li, a, span, mark`; `a`: `href` with schemes http/https/mailto only, `target`, and `rel` forced to `noopener noreferrer nofollow`; `span`: `style` limited to `color`; `mark`: `style` limited to `background-color`, and `data-color`. Anything else is removed (not rejected): scripts, event handlers, `javascript:` URLs, other tags/attributes/CSS properties. Text with no tags at all (API clients, old data) is converted to paragraphs, one `<p>` per line, HTML-escaped (an empty line is `<p></p>`), so line breaks are kept.
- **S4 — Limits.** The 500-character limit counts visible text (tags removed, entities decoded, ends trimmed): 1–500 characters. Blank visible text (e.g. `<p> </p>`) is rejected with 422. The sanitized HTML is limited to 10000 characters (422 above). Assumption: 422 messages follow the existing FastAPI default shape; the frontend keeps its counter "n/500" over visible text and its message 'El comentario no puede estar vacío.'.
- **S5 — Existing data (migration).** A new Alembic revision after `d2a8e5c3f7b1` widens `texto` of the three comment tables to `TEXT` and converts every existing comment with the S3 plain-text rule (escape + one `<p>` per line). Downgrade converts back to plain text (paragraphs/`br` → line breaks, tags removed, entities decoded), truncated to 500, and restores `VARCHAR(500)`. Formatting is lost on downgrade (documented).
- **S6 — Copy.** Copying workflow-step comments to subtasks keeps copying the stored (already sanitized) HTML verbatim, independent afterwards (unchanged behavior).
- **S7 — Contract and docs.** OpenAPI publishes the new limits for `texto`; docs/help that mention "1–500 caracteres" are updated.
