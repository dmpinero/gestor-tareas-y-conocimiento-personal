# subestado-y-comentarios-5000

Objective: comments accept up to 5000 characters instead of 500, and tasks get a new optional "Subestado" field (one per task) chosen from a catalog that works like the Etiquetas catalog; existing tasks and comments are migrated.
Branch: `feat/subestado-y-comentarios-5000` (worktree `../gestor-tareas-y-conocimiento-personal-worktrees/subestado`, based on main 7bc9890). Delivery: no commits until the user approves a preview (standing preference); then one PR, each migration in its own commit. Backend + 2 migrations + frontend.
Runners: backend `uv run pytest` (+ `uv run ruff check`, `uv run ruff format --check`, `uv run lint-imports`, `uv run bandit -r src -q`) ALWAYS with `URL_BASE_DATOS` exported to a throwaway MySQL (port 3308), never the real DB; frontend `pnpm vitest run`, `pnpm exec vue-tsc --build`, `pnpm exec eslint src`, `pnpm exec oxlint src`, `pnpm exec prettier --check src e2e`.

## Specs

User request (verbatim): "amplía los comentarios de 500 a 5000 caracteres. Incluye un nuevo campo Subestado (no obligatorio), que sea como el de las Etiquetas. Actualiza todas las tareas actuales con estos cambios."
User decision (verbatim option chosen): "Uno solo (Recomendado)" — described as: "Catálogo de subestados igual que el de etiquetas: se gestiona en Ajustes, se puede crear desde el formulario y se muestra como píldora de color. Pero cada tarea tiene como máximo un subestado, que es lo habitual en un estado."

- **S1 — Comentarios de 5000.** "amplía los comentarios de 500 a 5000 caracteres": the visible-text limit of comments (task, subtask, workflow step; rule defined in `odd/tasks/comentarios-con-formato.md` S4) becomes 1–5000 instead of 1–500, in backend validation, OpenAPI, the editor counter ("n/5000") and its typing limit, and every message/help/doc that says 500. Images keep not counting (see `odd/tasks/capturas-en-comentarios.md`). The sanitized-HTML cap (today 10000) is raised proportionally (assumption: 50000) so 5000 formatted characters fit; the comment `texto` columns of the three comment tables are widened as needed (assumption: MEDIUMTEXT) by a new Alembic revision after head `f1a6c3e8b2d9`, without changing any existing comment content. Downgrade restores the previous type only if no row exceeds it (otherwise fails with a clear message; assumption).
- **S2 — Catálogo de subestados.** A new catalog "Subestados" that works like the Etiquetas catalog in every place etiquetas have catalog behaviour: same management screen/flows in Ajustes (list, create, rename, delete, uniqueness/normalization rules of names as in `dominio/nombres_catalogo.py`), same API shape (`/api/v1/subestados` mirroring `/api/v1/etiquetas`), same color assignment style for its pill, creation from the task form if etiquetas can be created there.
- **S3 — Campo Subestado en la tarea.** Each task has at most one subestado (optional; "no obligatorio"). It can be set/changed/cleared when creating and editing a task (form control like the etiquetas selector but single-choice), and is shown as a colored pill wherever etiquetas are shown for a task (list column — hideable like the other columns —, detail, board card), filterable in the list like etiquetas (assumption: same filter UI, single field), sortable if etiquetas are, and included in exports if etiquetas are. Deleting a subestado from the catalog leaves its tasks without subestado (assumption: same as deleting an etiqueta). API: task responses gain an optional `subestado` (null when none); create/update bodies accept it optionally; existing bodies without it keep working (an update without the field does not clear it, matching how optional fields behave today — check and follow the existing PATCH/PUT semantics).
- **S4 — Tareas existentes.** "Actualiza todas las tareas actuales con estos cambios": a new Alembic revision (after S1's) creates the subestados catalog and the nullable task column (FK, ON DELETE SET NULL); every existing task gets no subestado (NULL) and all other data is unchanged; existing comments keep their content and accept up to 5000 after the change. Downgrade drops them.
- **S5 — Docs.** README/help that mention the 500 limit or list task fields are updated.

- **S6 — Agrupar por subestado.** "ahora quiero poder agrupar las tareas por subestado para poder verlas de forma más compactada en las vistas" — decision (L10): "sí, en lista y tablero". (assumptions below; frontend only)
  - List: a toggle "Agrupar por subestado" in the list toolbar; when on, the table is split into collapsible sections, one per subestado present in the filtered tasks (ordered like the catalog, by name) plus "Sin subestado" last; each section header is a button (aria-expanded) with the subestado pill/name and its task count ("En revisión · 4"). Sorting, filters, search and column visibility apply inside groups; export stays a flat list.
  - Board: the same toggle in the board view; inside each state column the cards are grouped by subestado in collapsible blocks with name and count; drag & drop and "Mover a…" keep changing only the state.
  - The toggle and the collapsed groups are remembered per view in this browser (localStorage, guarded with try/catch). Empty groups are not shown.
